# 07 — Make It Yours

This is a worked example, not a product. It is useful in direct proportion to how much of it you
replace.

## Do this first — one hour, before anyone creates anything

| # | Action | Why now |
|---|---|---|
| 1 | Rewrite [`naming-conventions.md`](../.github/standards/naming-conventions.md) | Retrofitting names onto live workspaces is the most expensive change on this list |
| 2 | Choose a promotion pattern, write the ADR | The first project becomes the template everyone copies |
| 3 | Replace the business terms in [`glossary.md`](../.github/standards/glossary.md) | Five real terms beat fifty example ones |
| 4 | Trim [`review-checklist.md`](../.github/standards/review-checklist.md) | A checklist longer than people will read is a checklist nobody uses |
| 5 | Set the workspace roles in [`security-and-access.md`](../.github/standards/security-and-access.md) | Especially "nobody has Contributor on prod" — agree it before someone needs it |
| 6 | Delete `projects/sales-analytics/` | Before someone mistakes Contoso for a real customer |

## Then

7. Write one **functional skill** for the thing newcomers get wrong in their first month. That skill
   is worth more than the other five combined, because it is the one nobody else could have written.
8. Add **project context** for your first real project. This is the single highest-leverage file for
   agent quality — more than any prompt engineering.
9. Turn on branch protection and secret scanning.

## What to keep

- The **shared core / per-workspace split**. It's the load-bearing idea.
- The **identity-layer rule** (never change `logicalId`, `type`, or an item folder name) and
  **one sync direction at a time**. Non-negotiable; it's how Fabric works.
- **Docs beside the directory, not inside it.** Small rule, saves a recurring argument.
- **ADRs.** Cheap to write, and they end the same debate arriving twice a year.
- **Installing rather than copying the Fabric skills.**

## What to change without hesitation

- Every naming pattern
- The item prefixes
- The example agents — your roles are not necessarily engineer / author / release manager
- The medallion layering, if you don't use medallion
- The CI jobs — add your own linting, your own DAX rules, your own tests

## Scaling

**Ten workspaces, one team** — as-is. Maybe collapse the project level.

**Fifty workspaces, several teams** — split by security boundary, not by size. A repo is a permission
boundary; if two teams should not see each other's work, that is two repos, not one repo with
careful folder conventions. Keep the shared core in a third repo and consume it as a submodule or a
published package.

**Multiple tenants or clouds** — one repo per tenant. Cross-tenant Git integration is not supported,
so the boundary is forced on you anyway.

## Where it stops working

Be honest about the limits so you notice when you have hit one:

- **Very large workspaces.** Fabric Git integration has file-size and folder-depth limits (25 MB per
  file, 10 levels). Big paginated reports and some semantic models get close.
- **Items not supported by Git integration.** Coverage has grown but is not complete. Check the
  current list before assuming everything in a workspace round-trips.
- **Binary-ish content.** Some item definitions are effectively unreviewable. Accept it, and lean on
  validation and testing rather than pretending review catches it.
- **Teams that won't commit.** Git integration does not auto-commit. A team that builds in Fabric and
  never presses Commit has a repository that is confidently out of date — which is worse than not
  having one.

## A note on the example project

`projects/sales-analytics/` is fictional. The company, the numbers, the SLA, the SAP quirks — all
invented, though the shapes are drawn from real engagements. The item folders under
`ws-sales-analytics-dev/` are hand-written, not generated by Fabric.

Read it, then delete it.
